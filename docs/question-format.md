# 문항 데이터 형식 가이드

새 지문·문항을 만들어 Firestore에 추가할 때 지켜야 할 형식을 정리한 문서다.
이 형식을 벗어나면 학생 화면에서 문항이 깨지거나, 채점이 틀리거나, 아예 출제되지 않는다.

> 발문을 어떻게 다양화할지는 별도 문서로 정리했다 → [문항 유형 카탈로그](./question-types.md)

> 이 문서의 모든 규칙은 실제 코드 기준이다.
> 검증 로직: [`scripts/audit-assets.mjs`](../scripts/audit-assets.mjs)
> 타입 정의: [`types/domain.ts`](../types/domain.ts)
> 지문 렌더링: [`utils/renderPassageContent.tsx`](../utils/renderPassageContent.tsx)

---

## 1. 전체 구조

데이터는 두 개의 Firestore 컬렉션으로 나뉜다.

```
assets              지문 1개 + 그 지문에 딸린 문항들   (한 문서 = 지문 1개)
learning_sessions   차시 1개 = 지문 4개를 묶은 단위    (한 문서 = 차시 1개)
```

학생이 진단을 시작하면 **차시 하나를 통째로 배정**받아 지문 4개를 순서대로 푼다.
차시 없이 지문만 있어도 동작은 하지만(지문 풀에서 4개를 임의로 뽑음), 차시로 묶는 쪽이 정상 경로다.

## 2. assets — 지문 문서

### 전체 예시

```jsonc
{
  "assetId": "a3f1c2d4-...",        // 문서 ID와 동일한 값 (UUID 권장)
  "gradeGroup": "초등 중학년",        // 아래 4개 중 하나만
  "subject": "식물의 한살이",         // 주제 (중복 출제 방지에 사용)
  "title": "씨앗에서 열매까지",        // 학생 화면에 보이는 제목
  "difficulty": "중",                // "하" | "중" | "상"
  "content": "지문 본문 ...",
  "status": "APPROVED",              // "CANDIDATE" | "APPROVED" | "REJECTED"
  "createdAt": "2026-08-01T10:00:00.000Z",
  "questions": [ /* 아래 3장 참고 */ ]
}
```

### 필드 규칙

| 필드 | 타입 | 규칙 |
|---|---|---|
| `assetId` | string | **Firestore 문서 ID와 반드시 같아야 한다.** 차시가 이 값으로 지문을 찾는다 |
| `gradeGroup` | string | `초등 저학년` / `초등 중학년` / `초등 고학년` / `중등` — 이 4개 문자열만 허용 |
| `subject` | string | 주제. 같은 학년군에서 이미 쓴 주제는 피하는 게 좋다 |
| `title` | string | 지문 제목 |
| `difficulty` | string | `하` / `중` / `상` |
| `content` | string | 지문 본문. 줄바꿈은 `\n` |
| `status` | string | `REJECTED`면 학생에게 **출제되지 않는다**. 필드가 없으면 사용 가능으로 간주 |
| `createdAt` | string | ISO 8601 문자열 |
| `questions` | array | 문항 배열 (3장) |

### 학년군별 지문 기준

[`data/curriculum.ts`](../data/curriculum.ts) 기준이다.

| 학년군 | 지문 길이 | 문장 길이(평균/최대) | 문체 |
|---|---|---|---|
| 초등 저학년 | 250~300자 | 10~15자 / 20자 | 단문 중심, 반복 구문, 친숙한 소재 |
| 초등 중학년 | 400~500자 | 15~25자 / 30자 | 인과관계 문장, 정보 전달문 |
| 초등 고학년 | 600~800자 | 20~30자 / 40자 | 논설문, 추상적 개념 |
| 중등 | 900~1200자 | 25~35자 / 50자 | 비평문, 논증적 구조 |

> 감사 스크립트는 지문이 **초등 저학년 200자 / 중학년 350자 / 고학년 500자 / 중등 800자** 미만이면 경고를 낸다.

## 3. questions — 문항

### 전체 예시

```jsonc
{
  "id": 1,
  "category": "사실적 이해",
  "question": "이 글에 따르면 씨앗이 싹트기 위해 필요한 것은?",
  "options": [
    "햇빛과 소리",
    "물과 알맞은 온도",
    "바람과 눈",
    "흙과 돌",
    "비료와 얼음"
  ],
  "answer": 2,
  "rationale": "2문단에 '씨앗은 물과 알맞은 온도가 있어야 싹을 틔운다'고 직접 제시되어 있다. 1번의 '소리'와 3번의 '눈'은 지문에 없는 정보이며, 4번의 '흙'은 언급되지만 싹트기 조건으로는 제시되지 않았다."
}
```

### 🔴 반드시 지켜야 할 것

**1) `options`는 정확히 5개**

4지선다는 허용되지 않는다. 감사 스크립트가 `critical`로 잡는다.

**2) `answer`는 1부터 시작한다 (0-based 아님)**

가장 사고가 잦았던 지점이다. 위 예시에서 정답이 `"물과 알맞은 온도"`(배열 2번째)이므로 `answer`는 **`2`**다. `1`이 아니다.

```
options[0] → answer: 1
options[1] → answer: 2
options[2] → answer: 3
options[3] → answer: 4
options[4] → answer: 5
```

학생 화면은 `optIdx + 1`을 정답과 비교하므로, 0부터 세면 **모든 채점이 한 칸씩 밀린다.**

**3) `category`는 아래 5개 한국어 문자열만**

```
어휘력 · 사실적 이해 · 추론적 이해 · 구조적 이해 · 비판적 이해
```

영어(`Facts`, `Inference` 등)나 변형(`사실적이해` 붙여쓰기)은 안 된다.
리포트의 역량별 점수가 이 값으로 집계되므로, 틀리면 그 문항은 어느 역량에도 반영되지 않는다.

**4) 선택지에 중복이 없을 것**

**5) 지문·문항·선택지에 HTML 태그 금지**

`<u>`, `<b>`, `<br>` 등을 쓰면 화면에 태그가 그대로 노출된다. 강조가 필요하면 5장의 마크업 문법을 쓴다.

### 선택 필드

| 필드 | 설명 |
|---|---|
| `id` | 지문 **안에서만** 고유하면 된다 (1, 2, 3...). 시험 출제 시 전체 통합 번호로 자동 재부여된다 |
| `rationale` | 해설. 없으면 경고. **오답 복습 화면에 그대로 노출**되므로 "정답인 이유 + 주요 오답이 틀린 이유"를 함께 쓴다 |
| `type` | `UNDERLINE_INTENT` 등 5종. ⚠️ **현재 화면 렌더링에 쓰이지 않는다** — 채워도 문항 모양은 달라지지 않으므로 분류 메모 용도로만 쓸 것 |
| `context` | 보기 박스. `{ "content": "보기 내용", "type": "BOX" }` — 문항 아래에 별도 상자로 렌더링된다 |

### 정답 번호 쏠림 주의

한 지문의 문항이 4개 이상인데 정답이 전부 같은 번호면 감사에서 경고가 뜬다. 1~5번에 고르게 분산시킨다.

## 4. 학년군별 역량 배분

한 차시(지문 4개) 전체 기준 권장 문항 수다. [`data/curriculum.ts`](../data/curriculum.ts)의 `categories` 값이다.

| 역량 | 초등 저학년 | 초등 중학년 | 초등 고학년 | 중등 |
|---|---|---|---|---|
| 어휘력 | 5 | 5 | 4 | 4 |
| 사실적 이해 | 5 | 5 | 5 | 4 |
| 추론적 이해 | 3 | 4 | 5 | 6 |
| 구조적 이해 | 0 | 2 | 3 | 5 |
| 비판적 이해 | 0 | 2 | 3 | 6 |
| **합계** | **13** | **18** | **20** | **25** |

초등 저학년은 구조적·비판적 이해를 **출제하지 않는다**. 리포트에서 "미평가" 영역으로 표시된다.

### 역량별 조작적 정의

| 역량 | 측정 대상 | 문항 형태 예시 |
|---|---|---|
| 어휘력 | 문맥 속 단어·관용구의 의미 | "밑줄 친 ㉠의 의미와 가장 가까운 것은?" |
| 사실적 이해 | 지문에 **명시된** 정보 확인 | "이 글에 따르면 ~한 것은?" |
| 추론적 이해 | 직접 드러나지 **않은** 의미 유추 | "이 글에서 알 수 있는 것은?", "빈칸에 들어갈 말은?" |
| 구조적 이해 | 글의 짜임·중심 내용 | "이 글의 중심 내용은?", "2문단의 역할은?" |
| 비판적 이해 | 글쓴이의 의도·논리적 타당성 평가 | "글쓴이의 주장에 대한 반론으로 적절한 것은?" |

## 5. 지문 마크업 문법

`content` 안에서 쓸 수 있는 특수 표기다. [`utils/renderPassageContent.tsx`](../utils/renderPassageContent.tsx)가 해석한다.

| 표기 | 화면 결과 | 용도 |
|---|---|---|
| `㉠[밑줄:솔솔]` | ㉠ 원문자 + "솔솔"에 굵은 밑줄 | 어휘력 문항의 대상 지정 |
| `㉡[문장밑줄:문장 전체]` | 문장 전체에 밑줄 | 문장 단위 지시 |
| `[빈칸]` 또는 `(   )` | 점선 빈칸 상자 | 빈칸 추론 문항 |
| `㉠`~`㉩` | 파란 원문자 배지 | 지문 내 위치 표시 |
| `ⓐ`~`ⓔ` | 초록 원문자 배지 | 보조 표시 |

### 🔴 마커 사용 규칙

**원문자만 단독으로 쓰지 말 것.** 반드시 `㉠[밑줄:대상텍스트]` 형태로 짝지어 쓴다.

```
✅ 빵 냄새가 ㉠[밑줄:솔솔] 나서 기분이 좋았어요.
   → 문항: "밑줄 친 ㉠'솔솔'의 의미로 알맞은 것은?"

❌ 빵 냄새가 ㉠ 솔솔 나서 기분이 좋았어요.
   → 어디에 밑줄인지 알 수 없다. 감사 스크립트가 경고를 낸다.
```

`[밑줄:...]` 안의 텍스트는 **지문 원문에 실제로 있는 표현과 정확히 같아야** 한다.

## 6. learning_sessions — 차시 문서

지문 4개를 하나의 시험 단위로 묶는다.

```jsonc
{
  "sessionId": "b7e2...",              // 문서 ID와 동일
  "gradeGroup": "초등 중학년",
  "title": "초등 중학년 3차시",
  "difficulty": "중",
  "assetIds": ["a3f1...", "c8d2...", "e5f9...", "b1a7..."],   // assets 문서 ID 4개
  "status": "APPROVED",                // "DRAFT" | "APPROVED" | "ARCHIVED"
  "createdAt": "2026-08-01T10:00:00.000Z"
}
```

| 항목 | 설명 |
|---|---|
| `assetIds` | **4개**가 기본. 여기 적은 ID의 지문이 실제로 존재해야 한다 |
| `status` | `ARCHIVED`면 출제되지 않는다. 검토가 끝나면 `APPROVED`로 |
| 중복 방지 | 학생이 이미 푼 차시는 자동으로 제외되고 다음 차시가 배정된다 |

## 7. 추가 절차

### 1) 작성

위 형식대로 JSON을 만든다. 지문 4개 + 그것을 묶는 차시 1개가 한 세트다.

### 2) 검증 — 업로드 **전에** 할 것

기존 데이터 점검용 스크립트가 있다.

```bash
node scripts/audit-assets.mjs --full
```

`🔴 심각(critical)`이 0건이어야 학생에게 내보낼 수 있다.

### 3) 업로드

현재는 아래 두 가지 방법이 있다.

**a. Firebase 콘솔에서 직접 입력**
Firestore Database → 데이터 → `assets` 컬렉션 → 문서 추가.
문서 ID를 `assetId` 값과 똑같이 지정해야 한다. 문항 수가 많으면 번거롭다.

**b. 업로드 스크립트 (미구현)**
JSON 파일을 읽어 검증 후 일괄 업로드하는 스크립트는 아직 없다.
정기적으로 추가할 계획이라면 이걸 만드는 편이 훨씬 안전하고 빠르다.

### 4) 관리자 화면에서 최종 확인

관리자 → **문항 검토** 탭에서 실제 렌더링 결과를 확인한다.
마커·빈칸이 의도대로 보이는지, 정답 번호가 맞는지는 여기서 눈으로 봐야 확실하다.

## 8. 체크리스트

새 지문을 추가할 때 이것만 확인하면 된다.

- [ ] `assetId`가 Firestore 문서 ID와 같은가
- [ ] `gradeGroup`이 정해진 4개 문자열 중 하나인가
- [ ] 지문 길이가 학년군 기준에 맞는가
- [ ] 모든 문항의 `options`가 **5개**인가
- [ ] `answer`가 **1부터 시작**하는 번호인가 (정답 선택지 위치 + 1)
- [ ] `category`가 정해진 5개 한국어 이름인가
- [ ] 정답이 한 번호에만 몰리지 않았는가
- [ ] 중복된 선택지가 없는가
- [ ] HTML 태그를 쓰지 않았는가
- [ ] `㉠` 같은 마커를 `㉠[밑줄:...]` 형태로 짝지어 썼는가
- [ ] `[밑줄:...]` 안의 텍스트가 지문 원문과 정확히 일치하는가
- [ ] 모든 문항에 `rationale`(해설)이 있는가
- [ ] 차시의 `assetIds`에 적은 지문이 모두 실제로 존재하는가
- [ ] `audit-assets.mjs`에서 critical 0건인가
